# BUG 卡：上传角色时控制台卡死/无响应（阿酉 · 2026-09-15 13:30 · 主人实测撞上）

> 主人报：一上传角色，控制台就卡死无响应。
> **根因基本确定：这就是我第二轮（09-14）就标了的 P1-1「上传对话框在 UI 线程做重活」——
> 缩图缓解了它，但没根治，现在真实用户撞上了。升级为 🔴 P0。**

---

## 一、根因分析

`ImportDialog` 的整条流水线——`pick()` → `reload()`（analyze + cutout_ai/cutout + split_views）
和 `accept_import()`（make_frames 21 帧变换）——**全部在 GUI 主线程同步执行**。

Windows 的规则：窗口超过约 5 秒不处理消息（点按钮、拖窗、重绘都不响应），就标「未响应」+ 白屏。
而完整版的 AI 抠图第一次使用要：加载 168MB 模型（10~60 秒）+ 推理（数秒）——
期间整个控制台冻结，看起来就是「卡死」。

诊断佐证：上传流水线**一条日志都没打**（ctl.log 只有 apply 记录），卡在哪一步、多久，
完全无法事后定位——这本身就是必须修的一部分。

## 二、给主人的即时缓解（不用等修复）

1. **完整版第一次上传时耐心等 1~2 分钟**，模型只加载一次，之后会快；
2. 或者上传时把抠图方式切到**「快速算法」**——不加载模型，秒级出结果；
3. 上传前先把图缩小到 2000px 以内（微信发一遍自己再保存即可）；
4. 卡住时**不要连点**——每点一次都是给主线程排更多任务，只会更久。

## 三、根治：线程化（方案已议定，这次必须做）

第三轮回执里你问过方案，我给过「**代数过期 + 单工作线程**」，现在落地它：

1. `ImportDialog` 加 `self._gen = 0` 和 `self._pool = QThreadPool(); setMaxThreadCount(1)`；
2. `reload()` / 档位切换：`self._gen += 1`，把 `analyze + cutout + split_views` 整段进 QRunnable；
3. Runnable 完成 → 信号回主线程 → **`if gen != self._gen: return`**（过期结果直接扔，
   用户连切档位不会互相踩）；单线程池天然串行，rembg session 无需加锁；
4. `accept_import()` 的 make_frames 同样处理，加「对话框已关闭则丢弃」判断；
5. 期间：按钮禁用、预览区显示「处理中…」、**光标用按钮禁用表达而不是 setOverrideCursor**
   （避免再碰那个栈）。

## 四、顺手补：上传流水线加日志

按 ctl.log 的风格给 `reload()` / `cutout 完成(耗时)` / `make_frames 完成(耗时)` 各打一行
到 logs/ctl.log——下次再报「卡」，回执里直接看耗时分布，不用猜。

- [ ] 快速连切 抠图方式/强度/角色 档位各 3 次：最终显示的是最后一次选择的结果（无串图）
- [ ] 生成桌宠期间界面不冻结，完成后自动切换新形象
- [ ] logs/ctl.log 能看到每步耗时
